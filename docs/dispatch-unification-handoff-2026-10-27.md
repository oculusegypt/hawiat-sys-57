# تقرير تسليم: توحيد المواعيد وأوامر العمل ومهام السائقين

**التاريخ:** 2026-10-27  
**الطلب:** توحيد البيانات والمسارات كاملة، وليس الاكتفاء بتوحيد الشاشة.  
**الحالة:** الاستكشاف اكتمل؛ التنفيذ بدأ لكنه غير مكتمل وغير متحقق.

## قرار المستخدم والنطاق

اختار المستخدم «البيانات والمسارات كاملة». المطلوب سجل تشغيلي واحد يكون مرجعًا للموعد، وأمر العمل، وإسناد السائق/الشاحنة، وحالة التنفيذ والإثبات، مع الحفاظ على السجلات التاريخية القديمة وربطها بدل حذفها.

لا يوجد إذن لنشر التغييرات أو لتغيير حالات المهام الحقيقية من دون دليل تشغيلي. لا تدمج سجلات متعارضة تلقائيًا.

## الوضع الحالي المؤكد من الشيفرة

- بيانات طلبات العملاء في جدول SQLite `service_requests`. يتضمن الجدول موعد الطلب وحقولًا مستقلة لإسناد السائق وحالته وإثباته.
- أوامر التشغيل من النوع `work_order` في `container_system_records`; تفاصيل الجدولة والإسناد وحالة السائق محفوظة في `payload` بصيغة JSON.
- المواعيد القديمة من النوع `appointment` في الجدول نفسه، لكنها سجلات منفصلة عن أوامر العمل.
- `GET /admin/work-orders` و`GET /driver/work-orders` يجمعان حاليًا صفوف `service_requests` وسجلات `work_order` في قائمة واحدة. أُضيف `recordType` لتجنب تصادم أرقام السجلات، لكنه لا يجعل مصدر البيانات موحدًا.
- تقويم التشغيل في `ContainerSystemSpecialPages.tsx` يقرأ سجلات `appointment`، ثم يحاول إيجاد أمر العمل بمطابقة `requestId` أو العقد أو الحاوية أو الموعد. المطابقة على وقت الموعد قد تربط سجلات غير مقصودة.
- فحص تعارض السائقين والشاحنات يقارن بين المصدرين، وهذا يمنع بعض الحجوزات المزدوجة لكنه يبقي حالتي البيانات منفصلتين.
- تدفق إنشاء العقد في Node ينشئ `work_order` بموعد مضمّن ولا ينشئ سجل `appointment` موازيًا. هذا الاتجاه مناسب ليكون `work_order` المرجع التشغيلي الواحد.
- يجب الحفاظ على تكافؤ واجهة Hostinger PHP؛ ملف المصدر هو `scripts/api-index.php` والملفات تحت `build_php/` نواتج بناء.

## قراءة بيانات آمنة أجريت أثناء التحقيق

كانت القراءة للمعرّفات والحالات والروابط فقط؛ لم تُقرأ أسماء العملاء أو الصور أو التواقيع:

- يوجد طلبا خدمة، وستة أوامر عمل، وسجل موعد واحد.
- طلب الخدمة `108` في حالة السائق `arrived` والطلب `in_progress`، وموعده `2026-10-12T07:00:00.000Z`، ويرتبط بالعقد `8044` والحاوية `413`.
- أمر العمل `8047` مكتمل، ويرتبط بالعقد `8044` والحاوية `413` وبالموعد `8046`، وله الوقت نفسه.
- طلب الخدمة `108` وأمر العمل `8047` مرشحان لأن يكونا تمثيلين للعملية نفسها، لكن حالتيهما متعارضتان. لا يمكن دمجهما بأمان دون مراجعة بشرية أو دليل تشغيلي.
- الموعد `8046` مرتبط صراحةً بأمر العمل `8047` بواسطة `workOrderRecordId`; يجب الحفاظ على هذا الرابط واستخدامه بدل التخمين.
- عند محاولة السائق إكمال الطلب `108`، منع API الإكمال لأن العقد مغلق والحاوية متاحة. هذا المنع صحيح لحماية سجل حركة الحاويات؛ لا تغيّر العقد أو الحاوية ولا تسجّل حركة بلا دليل.

## اتجاه التنفيذ المقترح

استخدم سجل `work_order` الحالي بوصفه السجل التشغيلي القانوني، تجنبًا لإضافة جدول موازٍ جديد:

1. ترقية طلب الخدمة إلى أمر عمل قانوني مرة واحدة، مع `legacyRequestId` ثابت ورابط تدقيق؛ يبقى طلب الخدمة محفوظًا كمصدر/سجل عملاء قديم، ولا يعود مصدرًا موازيًا لإسناد السائق أو تنفيذ المهمة.
2. ربط سجلات المواعيد القديمة بـ`work_order` عبر معرفات صريحة مثل `workOrderRecordId` و`appointmentRecordId`. إذا لم يوجد رابط صريح، لا تربط إلا بمطابقة مركبة فريدة موثوقة. إذا وُجد أكثر من مرشح أو تعارض في الحالة، احتفظ بالسجلين وعلّمهما لمراجعة الإدارة.
3. تخزين `scheduledAt`, `appointmentType`, `duration`, `assignedDriverId`, `assignedVehicleId`, `driverStatus`, وحقول الإثبات على أمر العمل القانوني. الموعد يصبح معلومات مرتبطة بالمهمة، لا سجل جدولة ثانٍ.
4. جعل قوائم الإدارة والسائق والتقويم تقرأ أوامر العمل القانونية فقط. أضف خيارًا لإظهار المكتمل في التقويم؛ قائمة العمل النشطة تظل محددة بالحالات النشطة.
5. اجعل مسارات الإسناد وتحديث السائق تعمل على `work_order` فقط. احتفظ بمسارات التوافق القديمة لكن اجعلها تحل `legacyRequestId` إلى أمر العمل القانوني قبل الكتابة.
6. عند إنشاء أو تعديل موعد من واجهة الإدارة، أنشئ/حدّث أمر العمل المرتبط داخل معاملة واحدة؛ لا تجعل تقويم التشغيل يعتمد على البحث التقريبي.
7. أظهر تحذيرًا إداريًا لأي سجل `reconciliationRequired`، وامنع انتقال السائق عليه إلى أن يُراجع. لا تدمج أو تلغي الحالات المتعارضة تلقائيًا.
8. طبّق السلوك نفسه في PHP/Hostinger، وحدّث اختبارات PHP المعزولة.

## التنفيذ الذي بدأ ولم يُتحقق منه

أُضيف الملف `artifacts/api-server/src/lib/dispatchCanonicalization.ts` لمحاولة ترقية طلبات الخدمة والمواعيد القديمة إلى سجلات `work_order`، مع تمييز المرشحين المتعارضين. **هذا الملف غير مكتمل وغير متحقق؛ لا تدمجه في مسارات API ولا تعِد تشغيل التطبيق قبل تصحيحه وفحصه.**

ملاحظة مهمة للمُكمل: توجد فيه حاليًا صياغة خاطئة في استدعائي `where()` داخل `linkAppointmentToWorkOrder`/مسارات الربط؛ راجعها وأصلحها باستخدام `eq(column, id)` من `drizzle-orm`. كذلك افحص type inference الخاص بنوع transaction قبل استخدامه، ثم أعد فحص كل شروط المطابقة والإدراج idempotent. لا تفترض أن الاختبار يمر.

## خطوات المتابعة الإلزامية

1. اقرأ هذا التقرير ومذكرات المشروع ذات الصلة: `shared-dispatch-resources.md` و`merged-work-order-identity.md` و`production-like-db-testing.md`.
2. افحص `git diff` الحالي أولًا للحفاظ على التغييرات السابقة غير المحفوظة. توجد تعديلات سابقة في:
   - `artifacts/api-server/src/routes/serviceRequests.ts`
   - `artifacts/sabaik-almasa/src/pages/admin/WorkOrders.tsx`
   - `artifacts/api-server/src/container-lifecycle.integration.test.ts`
3. أكمل الترحيل على نسخة اختبار SQLite مؤقتة فقط؛ لا تستخدم `data/sabaik.db` كقاعدة اختبار. لا تحذف أو تستبدل السجلات `108`, `8047`, `8046` ولا تغيّر العقد `8044` أو الحاوية `413`.
4. أضف اختبارات تثبت: الترحيل idempotent، الربط الصريح للموعد، منع الدمج عند تعارض الحالة، وعدم إنشاء حركة حاوية أو تغيير حالة عند المهمة المعلّمة للمراجعة.
5. وحّد Node API والواجهة، ثم نفّذ التوازي مع `scripts/api-index.php` واختبارات `scripts/test-php-container-lifecycle.php`.
6. شغّل `git diff --check` و`pnpm run typecheck` واختبار دورة الحياة المعزول واختبارات PHP. أعد تشغيل الخدمات ذات الصلة فقط بعد اكتمال التغييرات، ثم راجع السجلات.
7. لا تشغّل `drizzle push`, seed أو migration على قاعدة المصدر أثناء الاختبار. إذا أصبح تطبيق الترحيل على قاعدة المعاينة لازمًا، خذ نسخة احتياطية أولًا، تحقّق من العدادات والروابط قبل/بعد، وأبقِ التنفيذ إضافيًا وقابلًا لإعادة التشغيل من دون حذف.
8. لم يُنفّذ نشر.

## ملاحظات منفصلة من فحص المتصفح السابق

- تحذيرات XSLT/WASM الظاهرة كانت من إضافة Chrome، لا من ملفات التطبيق. لا تخفف CSP لإخفائها.
- طلبات API ظهرت في السجل مع تحويل Replit Shield وبعض `502/CORS`، مع أن الواجهة تستخدم مسارات API نسبية وسجل API المحلي أظهر استجابات ناجحة للطلبات التي وصلت إليه. تعامل معها كمسألة معاينة/Proxy منفصلة ولا تغيّر إعدادات CORS أو تستخدم روابط API مطلقة بلا دليل.
- تم إصلاح رسالة فشل الإكمال في واجهة السائق لتُظهر رسالة API الفعلية، كما تُعاد الاستفادة من رابط صورة الإثبات حتى انتهاء صلاحيته. فحص الأنواع واختبار دورة الحاويات المعزول اللذان سبقا بدء عمل التوحيد نجحا، لكنهما لا يتحققان من الملف الجديد أعلاه.
